En una arquitectura **N-Tier** (multicapa), la capa de **Controladores** (o *Controllers*) actúa como el **orquestador y punto de entrada** de las peticiones que provienen del cliente o de la capa de presentación.

Su principal función es recibir las solicitudes del usuario, coordinar la ejecución de la lógica necesaria y devolver la respuesta adecuada.

---

### Funciones principales

* **Recepción de peticiones (Routing & Endpoint Handling):** Escucha y responde a los eventos o solicitudes HTTP (GET, POST, PUT, DELETE, etc.) exponiendo la API o los puntos de acceso del sistema.
* **Validación inicial de entrada:** Comprueba que la petición contenga los datos necesarios, con el formato y estructura correctos (por ejemplo, validando los campos de un objeto JSON enviado por el usuario) antes de procesarlos.
* **Orquestación y delegación:** No ejecuta la regla de negocio ni accede directamente a la base de datos; delega el procesamiento real a los servicios de la **Capa de Negocio** (*Business Logic Layer / BLL*).
* **Mapeo de datos (DTOs):** Transforma los datos que entran (recibidos desde la vista o API) en modelos de dominio que la lógica de negocio pueda entender, y viceversa.
* **Formateo de la respuesta:** Convierte los resultados entregados por la capa de negocio en el formato adecuado para el cliente (por ejemplo, respuestas HTTP con códigos de estado como `200 OK`, `400 Bad Request`, `404 Not Found`, etc., empacadas en JSON o XML).
* **Manejo de errores a nivel HTTP:** Captura excepciones o errores generados en las capas inferiores y los traduce a respuestas inteligibles y estandarizadas para el cliente.

---

### Flujo de interacción en N-Tier

```
[ Capa de Presentación / Cliente ]
               │  (Petición HTTP / Evento)
               ▼
   [ CAPA DE CONTROLLERS ] ◄── Validaciones de entrada y respuesta HTTP
               │  (Llamada a métodos)
               ▼
 [ Capa de Negocio (BLL) ] ◄── Reglas de negocio y procesos
               │  (Consultas / Persistencia)
               ▼
 [ Capa de Datos (DAL) ] ◄── Acceso a Base de Datos

```

---

### Lo que NO debe hacer un Controlador (Anti-patrones)

1. **Lógica de negocio:** No debe contener reglas sobre cómo se calcula un descuento, cómo se valida una regla de dominio compleja o cómo se procesa un pago.
2. **Acceso directo a la base de datos:** Nunca debe ejecutar consultas SQL o usar directamente el ORM (*Entity Framework, Hibernate, Prisma, etc.*); esa responsabilidad pertenece a la Capa de Datos (*DAL / Repository*).
3. **Controlador "Gordo" (Fat Controller):** Acumular demasiadas responsabilidades en el controlador dificulta la realización de pruebas unitarias y desdibuja la separación de capas.

---

# Manejo global de errores, respuestas estandarizadas y capa de controller en Express 5

Guía para eliminar los `try/catch` repetidos, centralizar el manejo de errores, estandarizar las respuestas exitosas y separar responsabilidades entre router, controller y manager.

## Requisitos

- Express 5 (`"express": "^5.0.0"` o superior). En Express 5, un handler `async` que lanza o rechaza llama automáticamente a `next(err)`, por eso no hace falta `try/catch` ni un wrapper `asyncHandler`.
- `"type": "module"` en el `package.json`.
- `app.use(express.json())` registrado antes de las rutas.

## Responsabilidades por capa

| Capa | Responsabilidad |
|---|---|
| Router | Define paths y métodos HTTP, nada más |
| Controller | Lee `req`, valida el id, llama al manager, lanza `NotFoundError` y responde con `ApiResponse` |
| Manager | Reglas de negocio y acceso a datos. No sabe nada de HTTP |
| `globalErrorHandler` | Convierte errores en respuestas HTTP |

Flujo de una petición:

```
Request -> Router -> Controller -> Manager
                         |             |
                         v             v (lanza AppError)
                    ApiResponse   globalErrorHandler -> Response
```

## Estructura de archivos

```
src/
  errors/AppError.js
  utils/ApiResponse.js
  middlewares/errorHandler.js
  controllers/ServiceController.js
  routes/services.router.js
  managers/ServiceManager.js   (solo cambia el throw de validación)
  app.js
```

## 1. Errores personalizados

```js
// src/errors/AppError.js
export class AppError extends Error {
    constructor(message, statusCode = 500) {
        super(message)
        this.name = this.constructor.name
        this.statusCode = statusCode
    }
}

export class ValidationError extends AppError {
    constructor(message = 'Datos inválidos') {
        super(message, 400)
    }
}

export class NotFoundError extends AppError {
    constructor(message = 'Recurso no encontrado') {
        super(message, 404)
    }
}
```

## 2. Respuestas exitosas (2xx)

```js
// src/utils/ApiResponse.js
export class ApiResponse {
    static #send(res, statusCode, payload, message) {
        return res.status(statusCode).json({
            status: 'success',
            ...(message && { message }),
            payload
        })
    }

    // 200: la operación se completó y se devuelve un recurso o una lista
    static ok(res, payload = null, message) {
        return ApiResponse.#send(res, 200, payload, message)
    }

    // 201: se creó un recurso nuevo
    static created(res, payload = null, message) {
        return ApiResponse.#send(res, 201, payload, message)
    }

    // 202: la petición se aceptó pero se procesa de forma asíncrona
    static accepted(res, payload = null, message) {
        return ApiResponse.#send(res, 202, payload, message)
    }

    // 204: éxito sin contenido (no lleva body)
    static noContent(res) {
        return res.status(204).end()
    }
}
```

### Cuándo usar cada método

| Método | Status | Caso típico |
|---|---|---|
| `ok` | 200 | GET, PUT, PATCH y DELETE con respuesta |
| `created` | 201 | POST que crea un recurso |
| `accepted` | 202 | Tareas en segundo plano (envío de mails, procesamientos largos) |
| `noContent` | 204 | DELETE o PUT donde no hace falta devolver nada |

## 3. Middleware global de errores

Los cuatro parámetros `(err, req, res, next)` son obligatorios para que Express lo reconozca como middleware de errores.

```js
// src/middlewares/errorHandler.js
import { AppError } from '../errors/AppError.js'

export const globalErrorHandler = (err, req, res, next) => {
    if (res.headersSent) return next(err)

    if (err instanceof AppError) {
        return res.status(err.statusCode).json({
            status: 'error',
            message: err.message,
            payload: null
        })
    }

    // Error inesperado: se registra en el servidor y no se filtra al cliente
    console.error(err)
    return res.status(500).json({
        status: 'error',
        message: 'Error interno del servidor',
        payload: null
    })
}
```

## 4. Controller

```js
// src/controllers/ServiceController.js
import { NotFoundError, ValidationError } from '../errors/AppError.js'
import { ApiResponse } from '../utils/ApiResponse.js'

export default class ServiceController {
    #manager

    constructor(manager) {
        this.#manager = manager
    }

    // Convierte y valida el id de la URL
    #parseId(raw) {
        const id = Number(raw)
        if (!Number.isInteger(id) || id <= 0) {
            throw new ValidationError('El id debe ser un entero positivo')
        }
        return id
    }

    // Arrow functions como propiedades: no se pierde el `this` al pasarlas al router
    getAll = async (req, res) => {
        let services = await this.#manager.getServices()
        const { category, available } = req.query

        if (category) {
            services = services.filter(s => s.category.toLowerCase() === category.toLowerCase())
        }
        if (available !== undefined) {
            services = services.filter(s => s.available === (available === 'true'))
        }

        return ApiResponse.ok(res, services)
    }

    getById = async (req, res) => {
        const item = await this.#manager.getServiceById(this.#parseId(req.params.sid))
        if (!item) throw new NotFoundError('Servicio no encontrado')

        return ApiResponse.ok(res, item)
    }

    // La validación del body vive en el manager y lanza ValidationError
    create = async (req, res) => {
        const newService = await this.#manager.addService(req.body)

        return ApiResponse.created(res, newService, 'Servicio creado correctamente')
    }

    update = async (req, res) => {
        const updated = await this.#manager.updateService(this.#parseId(req.params.sid), req.body)
        if (!updated) throw new NotFoundError('Servicio no encontrado')

        return ApiResponse.ok(res, updated, 'Servicio actualizado correctamente')
    }

    remove = async (req, res) => {
        const deleted = await this.#manager.deleteService(this.#parseId(req.params.sid))
        if (!deleted) throw new NotFoundError('Servicio no encontrado')

        // Opción A: 200 con el recurso borrado
        return ApiResponse.ok(res, deleted, 'Servicio borrado correctamente')

        // Opción B: 204 sin body
        // return ApiResponse.noContent(res)
    }
}
```

`#parseId` rechaza ids como `abc` o `-3` con un 400, antes de llegar al manager.

## 5. Router

```js
// src/routes/services.router.js
import { Router } from 'express'

export default function createServicesRouter(controller) {
    const router = Router()

    router.get('/', controller.getAll)
    router.get('/:sid', controller.getById)
    router.post('/', controller.create)
    router.put('/:sid', controller.update)
    router.delete('/:sid', controller.remove)

    return router
}
```

## 6. Cambio en el manager

Donde antes se lanzaba un error con `code = "VALIDATION_ERROR"`, se lanza la clase:

```js
// src/managers/ServiceManager.js
import { ValidationError } from '../errors/AppError.js'

throw new ValidationError('El precio debe ser mayor a 0')
```

## 7. Composición en app.js

Las instancias se crean en un solo lugar y cada capa recibe a la siguiente por constructor.

```js
// src/app.js
import express from 'express'
import config from './config/env.config.js'
import ServiceManager from './managers/ServiceManager.js'
import ServiceController from './controllers/ServiceController.js'
import createServicesRouter from './routes/services.router.js'
import { globalErrorHandler } from './middlewares/errorHandler.js'

const app = express()
app.use(express.json())

const manager = new ServiceManager(config.dbPath)
const controller = new ServiceController(manager)

app.use('/api/services', createServicesRouter(controller))
app.use(globalErrorHandler) // siempre al final, después de todas las rutas

export default app
```

## Formato de las respuestas

Éxito:

```json
{ "status": "success", "message": "Servicio creado correctamente", "payload": { "id": 1 } }
```

Error:

```json
{ "status": "error", "message": "Servicio no encontrado", "payload": null }
```

## Qué se resolvió

- Cero `try/catch` en routers y controllers: el error llega solo al middleware global.
- El mapeo de error a status code vive en un solo lugar.
- Los errores inesperados responden 500 con mensaje genérico, sin filtrar `e.message`.
- Todas las respuestas exitosas salen por `ApiResponse`, sin repetir `res.status(...).json(...)`.
- Éxito y error comparten las mismas claves: `status`, `message` y `payload`.
- El router quedó como índice de endpoints, el controller se puede probar con un manager falso y el manager no conoce HTTP.
